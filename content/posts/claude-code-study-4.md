## STUDY4_260819

오늘은 글을 쓴 날이 아니라 **도구를 시험한 날**이었습니다. 디자인을 통째로 바꿨다가 되돌렸고, 매일 글을 자동으로 만드는 일을 클라우드에 맡겨보려다 두 번 막혔습니다. 남은 커밋은 하나뿐인데 배운 건 그보다 많았습니다.

### 되돌리기와 빌드는 다른 일이다

블로그를 사이버펑크 느낌으로 전면 교체해 봤습니다. 네온 색 제목, 어두운 배경, 좌우 2단 레이아웃까지 갔다가 결국 마음에 들지 않아 전부 폐기했습니다.

그 폐기 과정에서 헷갈렸던 게 있습니다. **"되돌려줘"와 "다시 빌드해줘"가 같은 말인 줄 알았습니다.** 전혀 다른 일이었습니다.

```
content/*.md          ← 원본 (내가 쓴 글)
static/styles.css     ← 원본 (디자인)
        │
        │  node src/build.mjs
        ▼
dist/                 ← 결과물 (브라우저가 보는 HTML)
```

| | 무엇을 바꾸나 | 비유 |
| --- | --- | --- |
| 되돌리기 | **원본**을 예전 상태로 | 원고를 예전 판으로 교체 |
| 빌드 | **결과물**을 원본에 맞춰 다시 생성 | 지금 원고로 다시 인쇄 |

**빌드는 원본을 절대 건드리지 않습니다.** 원본을 읽어서 `dist/`를 새로 구울 뿐입니다.

그래서 원본이 사이버펑크인 채로 빌드를 백 번 돌려도 사이버펑크가 나옵니다. 빌드는 결정적이라 같은 입력이면 언제나 같은 출력이니까요. 순서는 언제나 **되돌리기 → 빌드**입니다. 되돌리기만 하고 빌드를 안 하면 원본은 원래 디자인인데 화면에는 사이버펑크가 남아 있게 됩니다.

위험도도 다릅니다. **되돌리기는 되돌릴 수 없습니다.** 빌드는 몇 번을 돌려도 원본이 그대로라 위험이 없지만, 되돌리기는 저장하지 않은 작업을 지웁니다. 실제로 오늘 지운 파일 하나는 깃에 한 번도 들어간 적이 없어서, 지우면 복구할 방법이 아예 없었습니다. 미리 백업해 두고 지웠습니다.

그런데 정작 제일 애매했던 건 명령어가 아니었습니다. **"변경사항이 어디까지인가"**였습니다. 디자인 파일만인지, 그 사이에 만들어진 글까지인지. 이건 "돌려줘"라고 하든 "빌드해줘"라고 하든 풀리지 않습니다. 기준이 되는 지점을 짚어줘야 정리됐습니다.

### 스케줄러는 목표물이 어디 있느냐로 정해진다

매일 저녁 STUDY 회차를 자동으로 만드는 일을 다시 꺼냈습니다. 예전에는 결론이 이랬습니다.

> 블로그가 내 PC에만 있다 → 클라우드는 손댈 수 없다 → OS 스케줄러뿐이다

**그런데 첫 줄이 더 이상 참이 아닙니다.** 소스를 깃허브에 올렸고, `master`에 푸시하면 자동 배포되게 해뒀습니다. 즉 **저장소에 푸시할 수 있는 것은 무엇이든 블로그에 글을 올릴 수 있습니다.**

| | 어디서 도나 | PC가 꺼져 있으면 |
| --- | --- | --- |
| Windows 예약 작업 | 내 PC | 안 됨 (다음 부팅 때 실행) |
| GitHub Actions | 깃허브 서버 | 됨 |
| 클라우드 루틴 | 클라우드 | 됨 |

전에는 2·3번이 후보조차 못 됐는데 지금은 셋 다 됩니다. **도구가 늘어난 게 아니라 목표물이 옮겨간 것**입니다.

다만 원래 반대 이유 하나는 아직 남습니다. **스케줄러는 그날 무엇을 배웠는지 모릅니다.** 이건 권한 문제가 아니라 정보 문제라서 깃허브에 올렸다고 풀리지 않습니다.

### 권한에 두 번 막혔다, 서로 다른 이유로

클라우드 루틴을 만들어 봤습니다. 두 번 막혔는데 원인이 달랐습니다.

**첫 번째 — `401`.** 루틴을 저장하는 것 자체가 거부됐습니다.

```
Connect your GitHub account before saving a routine that uses a GitHub repository.
```

저장소가 공개라 누구나 읽을 수 있지만, **클라우드가 내 계정으로 무언가 하려면 별도 연결이 필요합니다.** 웹 화면에서 저장소를 한 번 선택해 주니 같은 요청이 그대로 통과했습니다. 바뀐 건 코드가 아니라 권한 하나였습니다.

**두 번째 — `403`.** 이번엔 루틴이 실제로 돌았습니다. 그리고 마지막 한 걸음에서 멈췄습니다.

```
git push                 → 403
GitHub API push_files    → 403 Resource not accessible by integration
```

클론도 됐고 커밋 로그도 읽었는데 되돌려 보내지를 못했습니다. **읽기 권한과 쓰기 권한은 별개**였습니다. 첫 연결로 얻은 건 읽기까지였던 겁니다.

여기서 배운 게 하나 더 있습니다. 자동화를 붙일 때 **기능보다 권한에서 막히는 시간이 더 깁니다.** 그리고 그 벽은 한 겹이 아닙니다.

```
1단계  물리적으로 닿을 수 있나?   → 깃허브에 올려서 해결
2단계  계정이 연결돼 있나?        → 401
3단계  쓸 권한까지 있나?          → 403
```

### 실패했는데도 확인된 것들

푸시만 빼고 나머지는 전부 동작했습니다.

```
샌드박스 할당 → 저장소 클론 → 오늘 날짜 확인
→ 24시간 내 커밋 조회 → 기존 회차 문체 파악
→ 초안 작성 → 테스트 16개 통과 → 빌드 성공
→ 초안이 새지 않았는지 검증 → 커밋 생성 → 푸시 실패
```

특히 **초안이 사이트로 새어나가지 않았는지 스스로 세어본 것**이 눈에 띄었습니다. 소스에서 초안이 아닌 글 6개와 빌드 결과의 글 6개가 일치하는지 확인하고 넘어갔습니다.

막힌 뒤에는 재시도로 될 문제가 아니라고 판단하고 알림을 보내고 멈췄습니다. **될 때까지 두드리지 않는 것**도 자동화에 필요한 판단입니다.

다만 푸시가 안 됐으니 그 초안은 컨테이너와 함께 사라졌습니다. **작업 결과를 밖으로 내보내지 못하면 안 한 것과 같습니다.**

### 자동화가 쓸 수 있는 것과 없는 것

클라우드 루틴은 커밋을 읽어 글을 씁니다. 그래서 오늘 배운 것 중 무엇을 쓸 수 있었는지 따져보면 경계가 선명합니다.

| 오늘 배운 것 | 커밋에 남았나 | 자동화가 쓸 수 있나 |
| --- | --- | --- |
| 글 3편 발행 | 남음 | 쓸 수 있음 |
| 디자인 폐기 | **안 남음** — 커밋한 적 없음 | 못 씀 |
| 빌드와 되돌리기의 차이 | 안 남음 — 대화에만 | 못 씀 |
| 깃허브 연결과 권한 | 안 남음 — 저장소 밖 설정 | 못 씀 |

**오늘 배운 것 중 커밋에 남은 건 하나뿐입니다.** 시행착오는 대개 커밋으로 남지 않습니다. 되돌린 작업은 흔적조차 없고요.

그래서 자동 초안은 **완성된 글이 아니라 출발점**으로 두는 게 맞다는 생각이 들었습니다. 자동화가 사실관계를 모아 뼈대를 세우고, 사람이 "그래서 뭘 알게 됐는지"를 채우는 분업입니다. 이 글도 그렇게 쓰였습니다.

### 확인이 필요한 부분

- 깃허브 앱의 **쓰기 권한**을 다시 승인해야 루틴이 완주합니다. 그전까지는 매일 18시에 돌아도 마지막에서 `403`으로 멈춥니다
- 쓰기 권한을 준 뒤에는 **자동 커밋이 어디까지 손대도 되는지** 정해야 합니다. 지금은 새 초안 파일 하나만 만지도록 막아뒀습니다
- Windows 예약 작업과 클라우드 루틴이 둘 다 살아 있습니다. 하나로 줄일지, 알림은 클라우드가 하고 작성은 대화로 할지 정할 일이 남았습니다
