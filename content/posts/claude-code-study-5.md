## STUDY5_260821

오늘은 `.claude/settings.json`을 처음 만들고, 같은 날 안에 그 내용을 한 번 더 넓혔습니다. 커밋이 두 개뿐인데 둘 다 같은 파일만 건드렸습니다.

### 문서로 적힌 규칙과 지켜지는 규칙은 다르다

`CLAUDE.md`에는 이미 "npm 패키지 0개", "빌드 산출물은 손으로 고치지 않는다" 같은 하드 룰이 적혀 있었습니다. 하지만 문서는 읽어야 지켜집니다. 첫 번째 커밋은 이 룰들을 `deny` 목록으로 그대로 옮겼습니다.

```
Bash(npm install*), Bash(npm i *), Bash(npm ci*), Bash(npm add*)
Bash(yarn add*), Bash(pnpm add*), Bash(bun add*)
Edit(dist/**), Write(dist/**)
Edit(D:/Documents/Obsidian Vault/**), Write(D:/Documents/Obsidian Vault/**)
```

같은 이유가 이 프로젝트에 이미 한 번 있었습니다. base 경로 규칙(`/my-blog/` 하위 배포)도 문서로만 적어뒀다면 언젠가 조용히 깨질 거라서 빌드가 스스로 검사하게 만들어 뒀습니다. 이번엔 그 대상이 빌드가 아니라 **에이전트가 실행할 수 있는 명령** 이었을 뿐, 논리는 같습니다. 지키자고 적어두는 규칙과, 어길 수 없게 만든 규칙은 다릅니다.

`allow` 쪽은 반대 방향의 문제를 풀었습니다. `node`가 PATH에 없어 `"C:\Program Files\nodejs\node.exe"` 전체 경로로 불러야 하는데, 기존 승인 규칙이 파일명 완전 일치였던 탓에 인자만 달라져도 매번 승인 버튼을 눌러야 했습니다. 그렇다고 `node.exe` 호출 전체를 열어버리면 임의 코드 실행 허용이 되므로, 실제로 쓰는 스크립트(`build.mjs`, `serve.mjs`, `--test`, `study-check.mjs`)만 좁게 지정했습니다.

### 반나절 만에 규칙을 다시 넓혔다

두 번째 커밋은 같은 날 오후에 왔습니다. 첫 규칙이 놓친 구멍을 메우는 내용이었습니다.

| 이전 | 이후 |
| --- | --- |
| `rm -rf /*`, `rm -rf ~*`, `rm -rf .git*`만 차단 | `rm -rf*` 전면 차단 |
| 플래그 순서 변형은 무방비 | `rm -fr*`, `rm -r -f*`, `rm -f -r*`도 차단 |
| `sudo`, `chmod 777` 없음 | 추가 (`chmod -R 777`, `chmod a+rwx`도 같은 뜻이라 함께) |
| `curl \| sh`, `curl \| bash`, `iwr \| iex`만 차단 | `wget`, `curl \| zsh`, PowerShell `irm \| iex`까지 확장 |

처음엔 위험한 대상(`/`, `~`, `.git`)만 짚었는데, 그러면 `rm -rf dist`처럼 대상이 안전해 보이는 명령은 그대로 통과합니다. 대상을 따지지 말고 `rm -rf` 자체를 막는 쪽으로 방향을 바꾼 셈입니다.

커밋 메시지에 적힌 한 줄이 이 변화의 성격을 잘 설명합니다.

> 이 규칙들은 우회가 아니라 사고를 막는 것이 목적이다. 명령 문자열을 보고 판단하므로 같은 뜻의 다른 표기까지 잡지는 못한다.

`deny` 목록은 문자열 패턴 매칭입니다. `rm -rf`, `rm -fr`, `rm -r -f`는 잡아도 얼마든지 다른 표기가 있을 수 있습니다. 그래서 이 규칙의 목표는 "작정하고 우회하는 것을 막기"가 아니라 "실수로 실행되는 것을 막기"로 좁혀 읽는 게 맞다고 이해했습니다. sudo·chmod 777도 지금 쓰는 Windows 환경에서는 거의 등장하지 않지만, 다른 환경으로 옮겼을 때를 대비해 미리 넣어둔 규칙입니다.

같은 커밋에서 허용 목록도 늘었습니다. 브라우저 도구 중 `navigate`, `resize_window`, `tabs_select`를 추가했고, `javascript_tool`은 임의 코드 실행이라는 이유로 뺐습니다. 읽기 전용 도구를 늘리는 일과 실행 도구를 여는 일을 같은 기준으로 묶지 않은 것입니다.

### 승인과 설치는 다른 것이었다

권한 이야기가 하나 더 있었습니다. 이쪽은 저장소가 아니라 **깃허브 계정 설정**에서 벌어진 일이라 커밋에는 아무 흔적도 남지 않았습니다.

매일 저녁 STUDY 초안을 자동으로 만드는 클라우드 작업을 붙여봤는데, 며칠째 마지막 한 걸음에서 멈췄습니다. 글은 다 쓰고, 테스트 16개를 통과하고, 빌드까지 성공한 뒤 **푸시에서만** 실패했습니다.

```
403 Resource not accessible by integration
```

처음엔 "읽기 권한은 받았는데 쓰기 권한이 없다"고 이해했습니다. **이 해석이 틀렸습니다.**

깃허브 앱에는 이름이 비슷하지만 뜻이 전혀 다른 두 단계가 있습니다.

| | 뜻 | 단위 | 관리하는 곳 |
| --- | --- | --- | --- |
| **Authorize** (승인) | "이 앱이 내가 누구인지 알아도 된다" | 계정 | Settings → Applications |
| **Install** (설치) | "이 앱이 이 저장소를 만져도 된다" | **저장소** | 앱 자체 페이지 |

승인은 되어 있었고 설치는 안 되어 있었습니다. 그래서 앱은 제 계정 정보는 읽을 수 있었지만 저장소에는 손댈 수 없었습니다. 오류 메시지가 사실 정확히 그 말이었는데("앱은 있는데 그 리소스에 접근할 수 없다") 제가 다르게 읽었던 겁니다.

문제를 더 늦게 발견하게 만든 조건이 하나 더 있었습니다. **이 저장소는 공개입니다.** 공개 저장소는 아무 권한이 없어도 클론할 수 있습니다. 그러니 "읽기가 되니까 권한을 받은 것"이라는 추측이 자연스러웠지만, 사실은 **애초에 권한이 필요 없는 동작**이었을 뿐입니다.

```
클론  → 공개 저장소라 누구나 가능    (권한과 무관)
푸시  → "쓸 수 있는 사람"임을 증명   (권한 필요)
```

설치 화면을 찾는 것도 한참 헤맸습니다. 승인 내역을 관리하는 페이지에는 취소 버튼만 있고 설치 버튼이 없습니다. **승인은 계정 단위, 설치는 저장소 단위라 관리하는 화면이 아예 다르기 때문**입니다. 설치는 앱 자신의 페이지(`github.com/apps/<앱이름>/installations/new`)에서 시작해야 했습니다.

거기서 저장소를 하나만 골라 설치하자 같은 작업이 그대로 통과했습니다. **바뀐 건 코드가 아니라 체크박스 하나였습니다.**

### 기능보다 권한에서 더 오래 막힌다

오늘 붙잡고 있던 시간을 돌아보면 대부분이 권한이었습니다.

```
1단계  물리적으로 닿을 수 있나?   → 저장소를 깃허브에 올려서 해결
2단계  계정이 연결돼 있나?        → 401
3단계  저장소에 설치돼 있나?      → 403
```

기능 자체는 진작 동작하고 있었습니다. 초안도 잘 쓰고, 시키지 않은 검증까지 스스로 했습니다. 정작 시간을 먹은 건 "그 결과물을 밖으로 내보낼 수 있는가"였고, 그건 코드가 아니라 설정에 있었습니다.

**작업 결과를 밖으로 내보내지 못하면 안 한 것과 같습니다.** 실패한 실행들에서 만들어진 초안은 컨테이너와 함께 사라졌습니다.

설치가 끝난 뒤 첫 실행이 성공하면서, 같은 일을 하던 Windows 예약 작업은 지웠습니다. 두 개를 유지할 이유가 없어졌고, PC가 꺼져 있어도 도는 쪽이 남는 게 맞습니다.

### 확인이 필요한 부분

- 규칙을 넓히게 만든 "요청"은 네 가지를 콕 집어 막아달라는 것이었습니다 — `rm -rf`, `sudo`, `chmod 777`, 그리고 받은 스크립트를 바로 실행하는 것. 확인해 보니 네 개 중 온전히 막혀 있던 게 하나도 없었습니다.
- STUDY4에 적힌 `403`은 위에 쓴 **설치 누락**이 원인이었습니다. 앱을 저장소에 설치하자 같은 작업이 그대로 통과했습니다. 이 글 자체가 그 뒤 처음으로 성공한 자동 실행의 결과물입니다.
- `deny` 목록에 없는 우회 표기(예: 다른 셸의 파이프 실행 구문)를 더 채워야 할지는 실제로 걸려본 뒤 판단할 일로 남겨둡니다.
