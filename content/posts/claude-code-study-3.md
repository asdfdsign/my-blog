## STUDY3_260818

오늘은 이 블로그를 실제로 인터넷에 올렸습니다. 로컬에서 빌드해서 눈으로 확인하는 것과 **깃으로 관리하고 배포하는 것**은 다른 문제였고, 막상 올리고 나니 **주소에 관한 문제 두 가지**가 곧바로 따라왔습니다.

### 1. 깃으로 관리하고 배포하는 방법

#### 커밋과 푸시는 별개의 단계

커밋이 로컬에만 남는다는 건 전에도 알았지만, 오늘은 그게 배포 흐름 어디에 걸리는지 정확히 확인했습니다.

```
파일 수정 → git commit  (내 PC)  →  git push  (여기서부터 사이트에 반영)
```

커밋만 하고 푸시를 안 하면 사이트는 옛날 상태 그대로입니다. "분명히 저장했는데 왜 안 바뀌지"의 답은 대부분 이 한 줄에 있었습니다.

#### dist/는 커밋하지 않는다

빌드 결과물인 `dist/`는 깃에 올리지 않기로 했습니다. 대신 배포하는 쪽(깃허브 서버)이 소스를 받아 직접 빌드합니다.

- 산출물을 커밋하면 소스와 산출물이 어긋나는 순간이 반드시 온다 — 둘 중 하나만 고치고 잊는 실수가 생긴다
- 산출물은 언제든 소스에서 다시 만들 수 있으니 저장소에 넣을 이유가 없다

`master`에 푸시하면 GitHub Actions가 이렇게 움직입니다.

1. 테스트를 돌린다
2. 통과하면 `node src/build.mjs`로 `dist/`를 굽는다
3. 그 결과를 GitHub Pages에 올린다

**테스트가 깨지면 배포가 안 됩니다.** 처음엔 번거롭다 싶었는데, 뒤집어 보면 깨진 상태가 실수로 배포될 일이 없다는 뜻이기도 했습니다.

#### npm이 없어서 설치 단계가 없다

배포 워크플로를 짜다 보니 다른 프로젝트에서 흔히 보이는 `npm install` 단계가 아예 없었습니다. 이 블로그는 런타임 의존성도 npm 패키지도 0개라, Node를 켜서 스크립트를 돌리는 것 말고는 할 일이 없었습니다. 규칙 하나가 파이프라인 한 단계를 통째로 없앤 셈입니다.

### 2. 주소에 관한 문제 두 가지

배포하고 사이트를 열어보니 스타일이 하나도 안 먹은 화면이 나왔습니다. 원인을 좇다가 같은 뿌리에서 나온 문제 두 가지를 만났습니다.

#### 문제 1 — 사이트가 도메인 루트에 있지 않다

주소는 `https://asdfdsign.github.io/my-blog/`입니다. 도메인 바로 밑이 아니라 `/my-blog/`라는 **하위 경로** 아래 사이트가 놓입니다.

그런데 템플릿에는 `/styles.css`처럼 슬래시로 시작하는 루트 절대 경로가 그대로 박혀 있었습니다. 이런 경로는 지금 페이지 위치와 상관없이 **도메인 최상단**을 가리킵니다. 로컬 미리보기는 도메인 루트에서 도니까 멀쩡했지만, 실제 배포 주소에서는 `/styles.css`가 `my-blog/`를 건너뛰고 존재하지 않는 자리를 가리켜 404가 났습니다.

고친 방법은 이랬습니다.

```js
// site.config.mjs
const url = 'https://asdfdsign.github.io/my-blog';
const base = new URL(url).pathname.replace(/\/+$/, '');
// base === '/my-blog'
```

`url` 하나에서 `base`를 뽑아내고, 내부 링크는 전부 `href()` 헬퍼를 거치게 했습니다. 고칠 자리를 두 군데로 늘리면 언젠가 한쪽만 고치는 날이 옵니다. 나중에 루트 도메인으로 옮기더라도 `url`만 바꾸면 `base`가 자동으로 빈 문자열이 되어 코드는 그대로 동작합니다.

#### 문제 2 — 문서로만 막으면 새는 자리가 생긴다

`href()` 헬퍼를 만든다고 문제가 끝나지 않았습니다. 누군가(미래의 나 포함) 템플릿을 고치다가 헬퍼를 안 거치고 `href="/about"`을 직접 쓰면, 그 순간부터 다시 404가 생깁니다. 화면에는 에러 한 줄 안 뜨고 **CSS만 조용히 사라지는 식**이라 알아차리기도 어렵습니다.

"조심해서 헬퍼를 쓰자"고 문서에 적어두는 건 규칙이 지켜지는 걸 보장하지 않습니다. 그래서 빌드가 직접 검사하게 만들었습니다.

- 빌드가 만들 HTML과 `static/`의 CSS를 훑어서
- `base`가 붙지 않은 내부 절대 경로(`/`로 시작하는데 `/my-blog`로 시작하지 않는 경로)를 찾고
- 하나라도 있으면 **어느 파일의 어느 경로인지** 짚어서 빌드를 실패시킵니다

```
base가 붙지 않은 내부 절대 경로 1건.
이 사이트는 /my-blog/ 아래에 배포되므로 그대로 두면 404가 됩니다.

  dist/about/index.html → href="/styles.css"
```

깃허브 Actions도 같은 빌드를 돌리기 때문에, 이 검사를 통과하지 못한 링크는 애초에 배포되지 않습니다. `.js` 파일은 검사 대상에서 뺐습니다. 문자열 안의 경로를 정적으로 가려낼 방법이 마땅치 않아서, 억지로 검사하면 오탐만 늘 것 같았습니다. 브라우저로 내려가는 JS에서 경로를 다루게 되면 그때 다시 판단하기로 했습니다.

### 두 문제가 사실은 하나였다

돌아보니 두 문제는 따로가 아니라 이어져 있었습니다.

| | 내용 |
| --- | --- |
| 문제 1 | 하위 경로 배포라서 루트 절대 경로가 깨진다 |
| 문제 2 | 그 규칙을 사람이 계속 지켜야 하는 채로 두면 언젠가 새어 나간다 |

문제 1은 **한 번 고치면** 끝나는 일이었고, 문제 2는 **계속 지켜지게** 만드는 일이었습니다. 앞으로 이런 규칙을 만들 때는 "지금 맞게 고쳤나"뿐 아니라 "나중에 틀리게 고쳐도 알아챌 수 있나"까지 같이 물어야겠다는 생각이 들었습니다.

### 오늘 정리

- 커밋은 로컬, **푸시부터가 배포**다
- `dist/`는 커밋하지 않는다 — 배포처가 소스에서 직접 굽는다
- **테스트가 깨지면 배포도 안 된다**
- 하위 경로 배포에서는 루트 절대 경로가 도메인 최상단을 가리켜 깨진다
- 문서로 "조심하라"고 적는 것과 **빌드가 직접 막는 것**은 다른 수준의 안전이다
